# 账单导入

安装更新后的 requirements.txt，先执行 `python -m alembic upgrade head`。
启动 API 后，还需在 backend 工作目录启动独立进程：

```powershell
../.venv/Scripts/python.exe -m app.bill_worker
```

Docker Compose 已包含 `bill-worker` 服务，它等待 API 完成迁移并健康后启动。
账单队列使用 PostgreSQL，不依赖 Redis/Celery。多个 Worker 通过 SKIP LOCKED 领取任务，
心跳与 owner 校验避免旧执行者发布结果；进程中断后 90 秒可重新领取，连续中断最多自动尝试三次。
单个任务处理上限 10 分钟。解析在工作线程执行，模型调用分批保存进度。

前端账单页和对话页共用导入组件。上传上限 20MB，解析上限一万行。
同一账户应始终填写相同账户标记；不要填银行卡号。原文件保存在任务表中用于恢复，
正式入库前可放弃任务，连同暂存记录删除。已入库任务保留文件和导入审计信息。

上传返回任务 ID，不立即写入 bills。预览允许按组/按行确认分类、排除记录、下载错误报告。
个人商户缺少用途时保持待确认。规则仅在用户勾选后保存，按用户、平台、账户、商户名称、
商品描述和交易类型精确匹配；它不是经过平台验证的商户身份。同名商户可能存在歧义。
模型结果始终是建议；每次任务的分类调用受 CLASSIFICATION_MAX_BATCHES 限制，可点击继续处理。

同文件哈希只在同一用户、账户下复用。正式交易以用户、平台、账户、交易单号唯一。
旧版 source=xlsx/csv 的交易不会猜测账户，预览会标记冲突，需明确选择匹配行并确认迁移来源，
或排除。来源迁移只接受唯一且核心字段相同的历史交易，保留原账单 ID 与人工分类。
迁移按钮立即修改已核对的历史来源；放弃导入不会撤销该明确操作。

报表支持 raw（原始流水）与 consumption（消费净支出）两种口径。
消费按原交易时间归属，排除转账、红包、充值、提现、内部划转及性质不明记录。
用户明确给支出转账设置消费用途后，可以纳入消费。退款优先使用原交易的已知退款状态；
另有独立退款行时，用户可以在查询表格中填写原账单 ID 建立关联，也可以解除关联。
状态退款金额与关联退款金额取较大值并以原金额封顶，避免同一退款双重抵扣。
无法关联、原状态也未体现的退款不会被猜测抵扣。收入流水不等于实际收入，收支差不等于账户余额。

`query_bill` 的 accounting_mode=consumption 与报表使用同一净额表达式；明细保留原始金额。
账单查询不缓存，以便导入、分类和退款关联后立即看到更新。
