# ADR 0003：提示词分层，流程 Skill 按意图按需注入

- 状态：已接受
- 日期：2026-10-19
- 相关：`backend/app/agent/graph.py`（`CORE_RULES` / `PROCESS_SKILLS` / `SKILL_KEYWORDS`）

## 背景

账单域有一大堆细碎的流程规则：转账怎么查、金额边界是开区间还是闭区间、
批量建卡该用哪个工具、卡片分类怎么定……如果全部写进 system 常驻，
提示词会变得很长，且大部分规则与当前这一轮无关。

## 决策

提示词分两层：

- **`CORE_RULES`（铁律）常驻**：永远生效的行为约束（默认行动优先、写操作必经确认、
  不得编造 ID、长期记忆只存用户明确表达的内容等）。
- **`PROCESS_SKILLS`（流程 Skill）按需注入**：`intent` 节点用关键词匹配用户最新消息，
  命中才把对应 Skill 拼进 system。本轮无关的规则完全不出现。

`intent` 在**每一轮**（首轮和续轮）都会重跑，因此 system 始终贴合当前意图。

## 理由

1. **注意力**。规则常驻会稀释模型对关键约束的关注，尤其是小模型。
   只给本轮用得上的规则，模型更容易照做。
2. **成本**。system 每轮都要重发，精简直接省 token。
3. **路由复用**。同一次关键词命中既决定注入哪些 Skill，也决定分发到哪个领域子图
   （`detect_agent`），一份判断两处用，不需要额外的路由模型调用。

## 代价与替代方案

**代价**：

- **关键词匹配会漏**。比如用户说「那笔星巴克多少钱」里没有「账单」二字，
  可能命中不到 `skill_query`。目前靠 `general` 领域的通用 agent 兜底，
  但规则不会注入，行为可能不一致。
- 规则散落在 `PROCESS_SKILLS` 字典里，改一条规则要找到对应 Skill。

**已否决的替代方案**：

- *全部常驻*：最省事，但正是本 ADR 要避免的问题。
- *用 LLM 判断该注入哪些 Skill*：更准，但每次都要多一次模型调用，
  而且为了省 token 做一次额外调用，账算不过来。
- *向量检索 Skill*：对 6 条 Skill 来说过度设计；等 Skill 数量到几十条再考虑。

## 验证

`backend/tests/` 中 `test_intent_injects_skill_into_system`、
`test_intent_keeps_core_only_for_chitchat` 等用例覆盖注入与未注入两种路径。
