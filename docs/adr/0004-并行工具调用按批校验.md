# ADR 0004：并行工具调用按批校验，混合批只放行一个调用

- 状态：已接受
- 日期：2026-10-30
- 相关：`backend/app/agent/graph.py`（`_route_after_agent` / `make_run_tools_node` / `make_approve_node`）

## 背景

HITL 的判定点在路由，执行点在 `run_tools`，两者对「一次模型响应里有几个工具调用」的假设不一致：

- `_route_after_agent`（以及三个子图里的同名路由）只看 `last.tool_calls[0]`，
  用它决定走 `approve` 还是 `tools`；
- `approve` 节点也只处理 `last.tool_calls[0]`；
- `run_tools` 却遍历 `last.tool_calls` 的全部调用。

模型完全可以（而且在有多个独立子任务时经常）在一条 `AIMessage` 里发出多个 tool_call。
于是 `[query_bill, create_tracking_card]` 这个顺序会让路由看到第一个是只读工具，
直接放行到 `tools`，然后 `run_tools` 把第二个写工具也执行了——**用户从未见过审批卡，
卡片已经落库**。

修复前的复现：构造一条包含上述两个调用的消息，执行后数据里多出 1 张卡片，
事件流里出现的唯一 interrupt 是 `input_checkpoint`，`approval_created` 从未产生。

## 决策

确立一条显式不变量：**一条 AIMessage 内的并行工具调用，只允许「全部只读」或「仅含一个写工具」。**

实现放在 `run_tools`（唯一的执行入口），而不是分散到四条路由：

```python
all_calls = list(last.tool_calls)
if len(all_calls) > 1 and any(c['name'] in write_tools for c in all_calls):
    calls, dropped = all_calls[:1], all_calls[1:]
else:
    calls, dropped = all_calls, []
```

被拦下的调用不执行，但必须补一条 `ToolMessage`（OpenAI 协议要求每个 tool_call id
都有对应回执，否则下一轮模型调用会被 400 拒绝），并以
`PARALLEL_WRITE_BLOCKED`（`stage='policy'`、`retryable=True`）回执退回给模型，
令其逐个重发。

## 理由

1. **失败要朝安全的方向倒**。混合批无法在不改协议的前提下逐个人工确认（一次 interrupt
   只承载一个审批 payload），那就不要猜——只放行一个，其余的让模型重来。
2. **收敛点选在执行侧**。四条路由各改一遍容易漏（主图 1 处 + 子图 3 处），
   而 `run_tools` 是所有调用的唯一出口，改一处即覆盖全部路径。
3. **不破坏只读并行**。多个只读调用照常一起执行，延迟与 token 都不受影响；
   只有涉及写操作的混合批才会退化成一个一个来。

## 代价与已否决的替代方案

**代价**：

- 混合批里排在写操作之后的调用会被丢弃并重发，多一次模型往返。
- 模型需要理解 `PARALLEL_WRITE_BLOCKED` 的含义才会逐个重试；小模型可能反复犯同一个错，
  最终由 `max_tool_calls_per_run` 或 recursion_limit 兜住（不会死循环，但会浪费几次调用）。

**已否决的替代方案**：

- *路由改为「任一调用是写工具就走 approve」*：`approve` 只处理 `calls[0]`，
  于是会出现「给只读工具弹审批、写工具仍不审批」的错位，比原问题更糟。
- *在一个 `approve` 节点里连续 `interrupt` 多次*：LangGraph 支持，但 runner 当前
  一次只消费一个 interrupt，前端 ApprovalCard 也是单审批模型，改动面远大于收益。
- *维护 `approved_call_ids` 台账，逐调用放行*：语义最正确，但需要新增 state 字段、
  处理 reject 后的跳过逻辑，并同步前端多审批 UI。留作未来真正需要并行写操作时再做。

## 验证

`backend/tests/test_graph_routing.py`：

- `test_parallel_read_write_batch_does_not_bypass_approval`——读 + 写混合批：
  无 `approval_created`、写调用回 `PARALLEL_WRITE_BLOCKED`、库里零卡片
- `test_parallel_write_first_still_requires_approval`——写排在首位：仍走审批，
  批准后建卡成功，同批只读调用被拦下并回执
- `test_parallel_reads_all_execute`——全只读批量：两个调用都执行成功，不产生审批
