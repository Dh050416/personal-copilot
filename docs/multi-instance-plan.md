# Agent 多实例改造准备

当前尚不支持安全的多实例聊天执行。共享 PostgreSQL checkpoint 不等于执行互斥。

## 已确认的问题

- `api/chat.py` 的 thread_runtime、active、waiting_approval、pending 均为进程内状态。
- resume 在读取 checkpoint、检查审批后才置 active，两个请求可同时通过检查。
- 进程退出会丢失追加输入；当前 SSE 断开会取消 runner，不提供后台持续执行。
- 建卡、建日程的唯一约束冲突后，需要保存点回滚才能在同一外层事务查询首次结果。

## 实施顺序

1. 引入 PostgreSQL 会话运行记录、持久化追加输入表、审批决策记录及 Alembic 迁移。
2. chat/resume 必须先获取同一个会话的跨进程执行权，再读取和修改 checkpoint。
   第一版可采用独立连接持有 PostgreSQL advisory lock：连接失效必须取消执行，不能静默继续。
   不依赖只检查超时的租约，因为旧执行者可能继续写入；如使用租约，需要 fencing 机制。
3. 审批决策采用唯一键和原子状态转换。重复相同决策返回已有状态；冲突决策返回 409。
   审批领取与图 checkpoint 不属于同一个事务，必须记录处理中状态并设计崩溃后的核对恢复。
4. 追加输入持久化。读取不等于删除：注入 checkpoint 成功后才确认消费，使用稳定消息 ID 去重。
   处理最后一个检查点后到达的输入，避免消息永久积压或下一轮乱序。
5. 核查所有写工具的业务变更与幂等响应是否在同一个数据库事务提交；修复唯一约束竞争分支。
6. 保持现有直连 SSE；后台 Worker、事件回放和自动重启恢复单独实施，不作为第一版已有能力。

## 验收

- 两个独立进程共享测试数据库，同时 chat/resume，同一会话只有一个图执行者。
- 不同会话可以并行；不同用户相同 session_id 不串数据。
- 并发重复审批只产生一次业务写入，冲突决策不能覆盖首次决策。
- 输入发往另一个实例后可被执行者读取；重启后未消费输入仍存在。
- 执行者退出、数据库连接失效、客户端断连、审批过期均有明确释放与恢复行为。
- 同键并发建卡、建日程各只生成一条记录，两个调用均能得到首次结果。
- 所有实例共享令牌签名密钥、数据库、checkpoint 配置；核查连接池总预算。

## Nginx

参考 `deploy/nginx.local.conf`。仅演示 API 三实例转发，不表示以上验收已通过。
三个后端须分别监听 8001、8002、8003；现有 run.py 固定 8000，需后续支持启动参数。
前端通过同源代理或开发代理访问统一入口。不要自动重试非幂等 POST。
